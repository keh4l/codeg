# 同步上游到定制版

调用参数（可能为空，可能是这次要注意的事）：$ARGUMENTS

## 仓库约定（先确认，不符就停下问用户）

- 本地仓库：Mac 上 `/Users/keh4l/Documents/Github/codeg`，Linux 服务器上 `/www/gitroot/codeg`（Rust 编译放服务器，见 `CLAUDE.md`「定制版」一节）；`origin` = `keh4l/codeg`（fork），`upstream` = `spacering-net/codeg`（2026-10 从 `xintaofei/codeg` 迁来，旧地址会重定向；作者仍是 xintaofei）。
- `main`：只跟上游，**不在上面提交**；`keh4l`：定制版，fork 的默认分支，发版从这里打 tag；功能分支另开。
- 提交身份一律 `keh4l <2461454684@qq.com>`，用 `git -c user.name=keh4l -c user.email=2461454684@qq.com …` 传入，**不改 git config**。
- 只用 merge，**不 rebase、不 force push** `keh4l`（tag 都在它的历史上）。
- 同步全靠手动：第 1 步的 `gh repo sync` 把 `main` 快进到上游，再合进 `keh4l`。原来每天快进 `main`、开 `main → keh4l` PR 的 `sync-upstream.yml` 已于 2026-11-16 删掉（11-06 起 GitHub 就不再跑它的定时任务），不要再加回来。

## 步骤

1. **看现状**
   ```bash
   git status --short            # 必须干净，不干净先问用户
   gh repo sync keh4l/codeg -b main   # 等于网页 Sync fork；main 有自己的提交会失败 → 停下报告
   git fetch origin && git fetch upstream
   git switch keh4l && git pull --ff-only
   git rev-list --count keh4l..origin/main   # 0 = 已是最新，结束
   ```
2. **先记下定制清单**（合并时要护住的东西）：`git diff --stat origin/main...keh4l`。再读一遍这次上游的提交说明（`git log --format=%B keh4l..origin/main`）：上游做了和 fork 重叠的功能（下表里写着「上游自己做了…改用上游的方案」的那些）时不会有文本冲突，先和用户确认怎么处理。
3. **合并**
   ```bash
   git -c user.name=keh4l -c user.email=2461454684@qq.com merge origin/main
   ```
   没冲突也要做第 5 步验证。有冲突按第 4 步处理；想放弃：`git merge --abort`。
4. **解决冲突**：`git diff --name-only --diff-filter=U` 列出文件，逐个处理（规则见下表）。标记里 `HEAD` 是 keh4l（我们的），`origin/main` 是上游。整文件取一边用 `git checkout --ours|--theirs <file>`，但**文件里还有别的定制时不要整文件取上游**。改完 `git add`，再确认没有残留标记：
   ```bash
   grep -rnE '^(<<<<<<<|>>>>>>>)' src src-tauri/src src-tauri/tests .github docs README.md || echo clean
   ```
5. **验证**（合并后编译错误也是"冲突"：上游给 enum 加了 match、改了函数签名，fork 的代码要跟着补，见下方经验）。先跑完前端再跑 Rust，**不要并行**：桌面版编译要读 `pnpm build` 的产物 `out/`，构建途中它不存在，会报 ``resource path `../out` doesn't exist``。`tsc --noEmit` 不能省：0.41.1 起 `pnpm build` 用 `tsconfig.build.json`，不检查 `*.test.ts(x)`，vitest 也只去掉类型不检查，测试文件里的类型错误（上游改了类型、fork 的测试数据没跟上）只有它能发现。
   ```bash
   pnpm lint . && pnpm exec tsc --noEmit && pnpm test && pnpm build
   cd src-tauri
   cargo test --features test-utils
   cargo test --no-default-features --features server-bin --bin codeg-server --lib
   cargo test --no-default-features --features cli-bin --lib cli::
   cargo clippy --all-targets --features test-utils -- -D warnings
   cargo clippy --no-default-features --features server-bin --bin codeg-server --lib -- -D warnings
   cargo clippy --no-default-features --features mcp-bin --bin codeg-mcp -- -D warnings
   cargo clippy --no-default-features --features cli-bin --bin codeg-cli --lib -- -D warnings
   ```
   在 Linux 服务器上：直接跑 `/root/codeg-staging/run-gate.sh`（上面这些加 `browser:agent` 两项），它已经处理好 root 跑测试、测试线程和 `pnpm test --maxWorkers=50%`，原因见 `CLAUDE.md`「定制版」一节。
   上游改了 `install.sh` 时再跑 CI 的 install-sh 检查：`/bin/bash -n install.sh && /bin/bash scripts/test-install-stop.sh install.sh`。CI 带 `CODEG_INSTALL_TEST_STRICT=1`，本机没有免密 sudo 时它会在「另一个用户的进程」那一项报 FAIL（上游的脚本也一样），本地不带这个变量跑，那一项显示 SKIP。
   CI 用最新 stable Rust，本地可能更旧、漏掉新 lint。Linux 服务器的默认工具链就是 stable，先 `rustup update stable` 再跑上面的 clippy 即可，不用下面的旁路工具链。Mac 上查 CI 版本：
   `curl -fsSL https://static.rust-lang.org/dist/channel-rust-stable.toml | sed -n '/^\[pkg\.rustc\]/,/^version/{s/^version = "\([0-9.]*\).*/\1/p;}'`，
   用旁路工具链跑 clippy（不动默认工具链）：`rustup toolchain install <ver> --profile minimal -c clippy`，`CARGO_TARGET_DIR=/tmp/codeg-target-<ver> cargo +<ver> clippy …`，跑完删掉那个目录（约 4 GB）。
   若新 lint 报在**上游原有代码**上、上游 main 的 CI 也一样红，不在 fork 里修（避免以后冲突），告诉用户等上游修。
6. **提交并推送**：有冲突时 `git -c user.name=keh4l -c user.email=2461454684@qq.com commit --no-edit`，然后 `git push origin keh4l`。**推送后不等 CI 跑完**（2026-10-30 起，用户定的）：第 5 步的本地门禁和 CI 的 Linux 部分是同样的命令，CI 只多了 macOS、Windows 上的测试，约 75 分钟，macOS runner 在美国白天还常排不上。推完就汇报，CI 当时的状态和 run 链接写进汇报（`gh run list -R keh4l/codeg -w test.yml -b keh4l -L 1`），之后它失败了再看。用户要同步完接着发版时，合并提交先不推，和 `codeg-fork-release` 的发版提交一起推，只跑一遍 CI。
7. **汇报**：合进了多少个上游提交、哪些文件冲突、各自怎么解决、测试结果（本地门禁的结果，加上 CI 当时的状态）。**不要顺手发版**，发版用 `codeg-fork-release`，并先问用户。
